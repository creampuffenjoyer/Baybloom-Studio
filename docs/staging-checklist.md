# Restricted staging checklist

Status: planning; no hosting provider, domain or staging infrastructure is selected. Local security checks are documented in [the audit](security-audit.md). This checklist records work to run once that target exists; none of the hosted checks below is marked complete.

1. Select a maintained Node runtime supported by the installed dependencies. The local Node 22.4.1 produces engine warnings and is not the staging runtime baseline. The host must support Next.js Cache Components, private file delivery and the maintenance handler's 120-second execution window. Keep CLI/development servers private.
2. Use a separate database containing no customer data, separate provider credentials and private storage. Establish backup/restore before migrations. Follow [the historical-data preflight](phase-1-deployment.md), [operations guide](phase-2-deployment.md) and [personalized release activation](template-export-phase2.md). Review the additional [six-template release requirements](template-export-phase3.md). Do not overwrite retained releases or purchased snapshots.
3. Configure the canonical HTTPS site URL, Auth.js secret, verified email sender, Stripe **test-mode** credentials/webhook secret, private S3/R2 credentials and maintenance secret through the host's secret store. Never put secrets in public environment variables, repository files or query strings. Restrict staging access to the intended testers; ensure Stripe's callback can reach its signature-authenticated webhook without opening the rest of the site.
4. Verify the actual ingress overwrites untrusted forwarding headers and prevents direct access to the app port. Send spoofed `X-Forwarded-For` values and confirm they cannot reset the observed rate-limit identity. Check real TLS, Secure/HttpOnly/SameSite session cookies, private/no-store API responses and the security headers through the deployed CDN. Confirm same-origin previews still load.
5. Rehearse sign-up, verification, login, reset and password-change email flows with controlled recipients. Confirm unverified accounts cannot save drafts or upload through either legacy or placement controls, but can read existing content and remove photos. Permit outbound HTTPS to `api.pwnedpasswords.com`; verify breached-password refusal and screening-outage retry behavior without consuming reset tokens or changing stored credentials. Check the shared five/IP, three/email and 100/global hourly signup limits against expected traffic. Confirm disabled accounts and revoked sessions cannot access the editor or files. If Google is enabled, test the callback domain, existing-password-account linking refusal, new-account throttling and existing linked login during signup throttling with test accounts.
6. Rehearse Stripe test-mode checkout, a fully discounted order, duplicate submissions, duplicate/signed webhooks, expiry and refund. Confirm totals come from the server and private downloads require the correct owner, paid status and tier. Verify purchased snapshots and photo assets remain unchanged after subsequent draft edits. Check bucket ACLs deny public reads and presigned URLs expire.
7. Check the shared draft-photo budgets (100 MiB per draft, 200 MiB per account), including concurrent writes through different templates and older photo controls. Existing oversized drafts must remain readable and reducible. Purchased assets are outside this quota. Decide retention, signup abuse limits and a service-wide cost budget before unrestricted registration.
8. Configure the authenticated maintenance schedule and alerts using [the operations guide](phase-2-deployment.md). Verify successful scheduling, package delivery and email retry recovery, failed-job alerts, and a backup restore. Record actual results and owners in the audit; a local test pass does not establish these hosted properties.

Administrative MFA has additional release requirements in [the MFA guide](admin-mfa.md): apply its migration, provision and back up the independent encryption key, rehearse actual authenticator enrollment and recovery, check clock synchronization, and establish out-of-band operator recovery approval. These hosted checks remain pending. Public release also depends on trial/membership product decisions and authorization review when implemented. Strict script CSP and the remaining dependency findings retain the status recorded in the audit.
