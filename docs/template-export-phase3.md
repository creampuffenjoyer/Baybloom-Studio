# Phase 3: all eight purchased exports

Phase 3 extends the Phase 2 purchase and delivery contract to Coral Cove, Pine Ridge Lodge, Lumen Lake Villas, Isla Verde, Ember & Salt, and Still Water Spa. Harbor House and Bloomfield Gardens retain their existing support. All eight templates use explicit original/saved checkout choices, immutable source and purchase snapshots, copied owned photos, delivery retries, and purchaser-authorized private downloads.

## Export contract

`src/lib/personalization/export-templates.json` registers all eight templates at template version `1.0.0`, content version `1`. Each declares its photo catalog and personalization context property. `additionalImageGroups` describes older dedicated uploads: Harbor room photos and Coral villa/gallery photos. The shared slot resolver validates keys against these catalogs and writes local `/personalized/` assets without template-specific packaging branches. Existing hero and library precedence is preserved by each template's own provider.

| Template | Library context | Representative saved content verified in the standalone site |
|---|---|---|
| Coral Cove | `websitePhotos` | Villa name/price and experience name; gallery photo; dedicated villa/gallery uploads included |
| Pine Ridge Lodge | `pinePhotos` | Room name/price and dining introduction |
| Lumen Lake Villas | `lumenPhotos` | Villa name/price/setting and experience name; tour photo |
| Isla Verde | `islaPhotos` | Room name/price and journal title |
| Ember & Salt | `emberPhotos` | Restaurant story and dish name/description/dietary labels |
| Still Water Spa | `spaPhotos` | Treatment name/option price and package name |

Every proof also includes saved business details, home copy, accent color, hero image and a library photo. Domain fixtures are in `tests/helpers/phase3-exports.mjs`. Regression and database checks cover every library slot; browser checks render representative uploads on actual pages.

The generated provider casts validated JSON to its own context type because TypeScript widens JSON enum literals, including villa settings and dietary labels. Validation remains in snapshot capture and packaging. The generated root layout includes a Suspense boundary required by the installed Next.js version for client URL hooks.

## Reproduce locally

Use Node 24+ or a supported Node 22 release as described in Phase 1. The verification helper runs installs and builds sequentially, defaults Rust and libuv worker pools to two threads, clears database/payment/storage credentials from standalone children, and retains successful builds when their source fingerprint and build ID match.

1. Run `npm run templates:verify:phase3`. It generates six baseline projects, independently installs/builds each, creates locked source archives, captures rich snapshots, and independently installs/builds all six personalized projects. Google Fonts require network access during builds. `-- --stage=baseline` or `-- --stage=personalized` checks an already prepared stage.
2. Run `npm run test:exports:phase3` with Chrome installed. Six sequential production browser scenarios verify saved home/inner-page content, local photos, mobile layout, and absence of private Baybloom requests or page errors.
3. Run `npm test`, `npm run typecheck`, and `npm run lint`.
4. Run `npm run test:database` only with `.env.test.local` pointing to the isolated `_test` database. The guarded runner rejects application database URLs. It includes the six-template purchase integration suite alongside the existing commerce, draft and delivery suites.
5. Run `npm run test:purchase:phase3` with the isolated database migrated and the reviewed locked source archives present. It exercises real credentials, owned photo APIs, the fully discounted checkout UI, retry after draft deletion, maintenance delivery, six private downloads, anonymous/cross-account denial and refund denial. The suite restores prior active releases and removes its temporary database fixtures.

For shared computers, run these commands one at a time and use a lower process priority. Antivirus may scan the files generated by dependency installs and builds; retaining verified projects avoids unnecessary repeated filesystem work.

The storefront production build also requires at least one published catalog design: this Next.js version rejects empty `generateStaticParams` results with Cache Components. When building against an empty isolated test database, create a temporary published design and category, run the build with guarded test URLs, and remove those fixtures in `finally`. Do not seed the application database for this check.

## Proof artifacts

Generated files are ignored by Git under `storage/phase3/`:

- `release/deliverables/<template>/<template>-source.zip`: locked, versioned source archives.
- `personalized/<template>-personalized.zip`: saved-content standalone proofs; extracted projects retain independent dependencies.
- `verification.json` and `logs/`: successful source fingerprints, runtime, timestamps and individual build logs.
- `screenshots/`: standalone desktop and mobile screenshots.
- `purchases/`: authenticated purchase ZIPs and storefront screenshots.

Verified locally on 2026-11-10 using Node 24.22.2:

- All six baseline projects and six personalized projects passed independent production builds. Personalized projects installed their own dependencies with `npm ci` from exported lockfiles.
- All six standalone Chrome scenarios passed, including edited inner pages, local images, desktop/mobile rendering and no private requests or browser exceptions. Ember's saved vegan/gluten-free labels rendered with its edited dish.
- All 85 standard regression tests passed, including all eight original/saved choices, complete photo catalogs, separate Coral image groups, source integrity, isolation and deterministic retry packaging.
- All 24 existing PostgreSQL checks passed, and the new six-template integration suite passed all seven reported checks (six cases plus its parent). The new suite verifies copied image catalogs, draft deletion, source switching, priced checkout with the Stripe fixture, delivery and refund authorization. These were run against the isolated `baybloom_test` database. A reused mock Stripe session ID was corrected before the successful focused rerun; live Stripe was not called.
- One authenticated Chrome journey passed for all six real source archives in approximately 263 seconds. Saved content and owned photo uploads survived draft deletion, checkout retries reused the original order, maintenance prepared all six ZIPs, and private downloads enforced buyer/payment status. Desktop/mobile checkout and order views passed. Temporary users/catalog/coupon/order fixtures were removed and previous active releases restored.
- The storefront production build passed, generating 184 pages. Its temporary published catalog fixture was removed afterward.
- Final repository type checking and lint passed.

All purchased ZIP proofs are in `storage/phase3/purchases/`. The final checks ran sequentially at lower priority with two logical processors available to the process tree. No application database changes, production storage uploads, live payments, real emails, deployments or pushes were performed.

## Release preparation and limits

Follow `docs/template-export-phase2.md` for migrations, private storage, maintenance authentication, retry monitoring and retained-source backups. No new schema migration is required for these six registrations. Activate each reviewed source with `scripts/register-template-release.mjs <template> <source.zip>` only during an authorized application release; `--test` rehearses against the guarded test database. Code registration alone does not activate an application database release.

Forms, availability, booking, gift cards and subscriptions within exported templates retain their demonstration behavior. Edited English content is not automatically translated. Default page metadata and photo credits require customer launch review. Production S3/R2 upload and presigned downloads, real email, live payments and scheduler operation still require the isolated provider rehearsal described in Phase 2.

Existing user work and private deliverables are preserved. Application database release activation, deployment and pushing are outside this local verification.
