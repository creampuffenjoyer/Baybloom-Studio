# Application security audit — 2026-11-15

Scope: the current Baybloom storefront, authentication, account actions, catalog/pricing APIs, carts, checkout, Stripe handler, drafts/photos, purchase packaging, orders, private downloads and maintenance worker. This is a source-assisted application review with targeted browser/database tests, not a certification or a test of a hosted production environment. Trial entitlements, paid memberships and admin operations do not yet exist and cannot be signed off here.

Active checks use the guarded disposable `_test` database and temporary accounts. Payment, email, Google and cloud-storage credentials are cleared from the test application. No application database migration, live payment, real email, production release activation, deployment or push is authorized or performed by this audit.

## Confirmed issues and changes

| ID | Severity in this application | Finding | Resolution |
| --- | --- | --- | --- |
| SEC-01 | Medium | Cart/favorite JSON routes parsed JSON from a browser-simple `text/plain` POST without origin enforcement. A real Chrome page on a different, same-site origin added a favorite using ambient session cookies. SameSite cookies alone did not prevent this. | Fixed. Cookie-authenticated cart, coupon, favorite, password and checkout writes now require the same origin; JSON writes require the exact JSON media type. Delete operations also enforce origin. Server Actions retain Next.js origin/authorization checks; machine-authenticated Stripe and maintenance endpoints use their own authentication. |
| SEC-02 | Medium | Several authenticated JSON handlers and the unauthenticated Stripe signature parser could read an unbounded body before validation. | Fixed. JSON bodies are limited to 4 KiB while streaming, including absent or misleading Content-Length. Stripe receives the exact signed bytes with a 1 MiB bound. Existing image/draft byte and pixel limits remain in place. |
| SEC-03 | Medium advisory; restricted exposure | Installed `fflate` 0.8.2 was affected by malformed ZIP64 input that could block `unzipSync`. Purchased packaging uses this parser, though source ZIPs are reviewed operator inputs, not customer uploads. | Updated the installed dependency and lockfile to 0.8.3. A worker-isolated regression verifies malformed ZIP64 parsing terminates. Existing source-size, manifest, path, digest and image-slot checks remain active. |
| SEC-04 | Low / defense in depth | No explicit application-wide anti-framing or MIME-sniffing policy. | Added SAMEORIGIN framing, matching CSP frame-ancestors, object/base restrictions, nosniff, a referrer policy and production HSTS without forcing subdomains. Internal preview frames remain allowed. Disabled the framework identification header. This is a limited CSP, not a nonce-based script policy. |
| SEC-05 | Low / defense in depth | The local callback helper accepted control-character URL-normalization tricks. An end-to-end external redirect through Auth.js was not established; its own redirect validation provides another boundary. | Reject controls, whitespace and backslashes in callback paths while preserving ordinary encoded local destinations. |
| SEC-06 | Low | Catalog query accumulation used an ordinary object; `__proto__`, `constructor` and `toString` keys could select inherited properties and raise an exception. This is not a demonstrated prototype-pollution or SQL-injection exploit. | Accumulate query parameters in an object with no prototype. The API accepts these unexpected query names without a server error and ignores them during schema parsing. |
| SEC-07 | Medium policy / low truncation risk | New passwords could be eight characters without MFA, and could exceed bcrypt's 72-byte input boundary and be silently truncated. | New registration/change/reset passwords require 15 Unicode code points and must fit within 72 UTF-8 bytes. Form guidance matches the server policy. Existing logins remain compatible; stored hashes and customer passwords are not rewritten. |
| SEC-08 | Low reliability / defense in depth | Two simultaneous consumers of one reset/verification token could race the delete and produce a server exception. This was fail-closed, not a demonstrated token-reuse bypass. | An atomic conditional delete allows one consumer to succeed; other consumers return an invalid/expired result. The expiry condition is checked on the consuming write. |
| SEC-09 | Medium resource-abuse gap | The placement-only photo budget could be bypassed by legacy photo controls, hero saves or multiple templates. | A shared transaction now serializes photo growth on the account row before draft locks, checks every draft's stored hero and image bytes, and rolls back excess writes. All hero, room/villa, gallery, library and placement writes enforce 100 MiB per draft and 200 MiB per account. Replacements count their resulting size. Existing over-limit data is preserved; text edits and shrinking remain possible. Quota refusals return private JSON with status 413. No schema migration is needed. |
| SEC-10 | Medium authentication-policy gap | New passwords were not checked against breached credentials. | Registration, password changes and resets now use a bounded, four-second, padded Pwned Passwords range request. Only five SHA-1 hash characters are sent to a fixed HTTPS endpoint; no password, full hash, suffix or email is transmitted or logged. Positive counts reject the password; zero-count padding is ignored. Invalid/oversized responses, network errors and timeouts block setting the password with a retry message. Existing login remains available. Reset tokens are not consumed on screening refusal or outage. SHA-1 is used for the range protocol only; stored passwords continue to use bcrypt. |
| SEC-11 | Medium signup/storage-abuse gap | Unverified accounts could save drafts and upload photos, while account-creation controls covered only password signup's IP limit. | Every draft/image PUT is gated before parsing or image decoding against the account's current database verification status. Reads and deletion remain available. Password and new Google-account creation share database-backed limits of five attempts per IP/hour, three per email/hour and 100 account-creation attempts globally/hour. Existing linked Google sessions do not consume signup capacity. Reset submissions also have ten attempts per IP and five per token per 15 minutes. Limits fail closed on database failure; rate-limit keys are hashed. |
| SEC-12 | Administrative authentication-policy gap | Administrative sessions previously required only the primary login credential. | Mandatory authenticator/recovery-code verification for admins, with a constrained enrollment-only state before activation. Seeds are encrypted with a separate AES-GCM key and bound to the account; recovery codes are hashed. Account-row locks prevent TOTP/recovery replay. Setup requires a recent password sign-in, verified inbox and password re-entry; replacement also requires the current factor. MFA versions and revocation are rechecked on session reads. Email password reset retains MFA; administrative password changes require fresh MFA login. Google alone cannot establish an administrative session. See the MFA guide for release requirements and limitations. |

Code entry points: `src/lib/request-security.ts`, `src/lib/validators.ts`, `src/lib/urls.ts`, `src/app/api/`, `next.config.ts` and the package lockfile. Existing purchase, UI and template work is preserved. Browser integration callers now provide an explicit origin for the protected API writes.

## Attack classes reviewed

| Class | Evidence and practical limit |
| --- | --- |
| Stored/reflected/DOM XSS | React renders account/profile/draft values as text. The single raw HTML sink is product JSON-LD, which escapes `<` before insertion. Browser cases submit markup in names, catalog search and saved preview copy, and exercise script-closing JSON-LD data. Draft colors are restricted to hex; uploaded SVG/HTML is refused rather than sanitized into executable content. This does not establish that every possible browser payload is harmless. |
| SQL injection | ORM queries use validated values; every raw SQL call in application source uses Prisma tagged parameters. No unsafe raw-query API or SQL string concatenation was found. Search/download probes containing SQL metacharacters remain values, not instructions. No time-based database exhaustion or destructive SQL is attempted. |
| IDOR / BOLA / broken access control | Server queries bind draft/photo, cart, order, download and purchase access to the authenticated user. Two-account cases cover guessed objects, foreign cart deletion, private photos, unpaid/refunded orders, tier restrictions and attempted user/role assignment. UUID secrecy is not treated as authorization. |
| Broken authentication | Auth.js verifies encrypted session tokens and rechecks the database for disabled users, roles and session revocation. Password change/reset invalidates old sessions; reset/verification tokens are random, hashed and expiring. Existing regressions prohibit automatic OAuth adoption of password accounts. Real Google OAuth is not exercised without a provider sandbox. |
| CSRF / CORS | The original browser attack was reproduced and blocked after the fix. The route matrix checks absent, foreign, same-site sibling and null origins and browser-simple/JSON-lookalike media types. No wildcard credentialed CORS policy is added. |
| Payment and business-logic abuse | Prices are recomputed on the server. Checkout rejects forged totals/purchaser fields. Existing regressions and isolated database cases cover coupon races, duplicate requests, immutable purchase snapshots, provider-state mismatches, refunds and delivery fencing. The browser's fully discounted order uses no external payment API. Stripe signature tests use SDK-generated local fixtures, not real provider delivery. |
| Uploads / traversal / package integrity | Image bytes are decoded and normalized to bounded WebP, with fixed slot allowlists and owner-scoped storage. Source archive paths, manifests, digests and copied purchase assets are checked. Download authorization checks owner/payment/tier before issuing expiring URLs. Signed-link tampering and SVG-as-PNG probes are rejected. Already issued bearer links can remain valid for their five-minute lifetime after a refund, as documented. |
| SSRF / SSTI / command injection / XXE | No client-controlled server fetch target, shell execution, runtime template compilation or XML parser was found in application request handling. Provider URLs and storage endpoints are trusted operator configuration. Generated website content is serialized as JSON, not interpolated into executable source. |
| Secrets and private data | Current tracked files and public assets contain no application `.env`, private ZIP, PEM key or browser source map found by this pass. Git object paths showed `.env.example` only. Pattern checks did not find live-key/private-key matches in application/source/public paths. These are scoped checks, not a complete historical secret-scanner guarantee. Session-dependent catalog/cart/favorite responses explicitly prohibit shared caching. |

## Remaining risks and launch conditions

These need named release owners and verification; this audit does not mark public launch ready.

1. **Ingress and abuse controls — Medium, deployment owner.** IP-based throttles read `X-Forwarded-For`. The chosen ingress must overwrite untrusted forwarding headers and prevent direct public access to the application port. Verify this on staging. Per-user/email limits, password screening, a global hourly signup cap, verified-email storage gating and administrative MFA now exist. CAPTCHA and trial entitlement policy remain unimplemented. The signup ceiling is an abuse-control default to review against expected traffic, not a membership entitlement or a lifetime account cap. Do not expose development or CLI servers publicly.
2. **Storage governance — partially resolved, application/product owner.** Shared limits cover all saved draft photo paths: 100 MiB per draft and 200 MiB per account, with database serialization against concurrent growth across templates. This counts image bytes, including hero images and legacy controls, without transferring image blobs into application memory for accounting. Purchased snapshots and delivered files are outside the draft quota and are not deleted. The owner selected a [30-day retention proposal](storage-retention.md); a read-only aggregate report is implemented, while activity tracking, notices, entitlement rules and deletion remain pending. The application report currently identifies missing draft/photo tables and does not run migrations. Determined multiple-account abuse and an overall service budget still need policy. New draft saves and image uploads require email verification; trial/membership entitlements are not implemented.
3. **Authentication additions — partially resolved, authentication/product owner.** New passwords require 15 Unicode code points and are checked against breached passwords, while existing client login credentials remain usable. Administrative MFA is implemented; its migration, independent encryption key, backup/restore and operator recovery procedure are release prerequisites in [the MFA guide](admin-mfa.md). Client MFA and passkeys are not implemented; TOTP/recovery codes are phishable. Registration deliberately reveals an existing email; review that enumeration/UX tradeoff. Password screening is a new outbound dependency: permit HTTPS to `api.pwnedpasswords.com`, monitor availability without logging credentials or hash material, and rehearse an outage on staging. A screening outage temporarily blocks signup and setting/resetting passwords; existing login remains available. These are remaining controls, not evidence of an account-takeover bypass in the tested flows.
4. **Strict script CSP — Low defense-in-depth gap, frontend/security owner.** The new policy protects framing/base/object behavior, but does not restrict script sources. Nonce-based CSP requires a reviewed rendering strategy with this Cache Components setup; do not claim the current policy blocks arbitrary inline scripts.
5. **Dependency advisories — tooling owner.** The initial registry audit reported 26 affected package entries. Patching `fflate` reduced this to 25 (9 high). A subsequent compatible `npm audit fix --ignore-scripts`, without force or major-version changes, reduced it to 16: 3 high, 11 moderate, 2 low, 0 critical. The remaining three high entries are the `prisma` → `@prisma/config` → `deepmerge-ts` chain. That path merges trusted local configuration; the reported recursive-object condition is not produced by ordinary JSON and no HTTP path to it was found. Other findings remain in lint/component tooling. This is a reachability assessment, not a clean dependency audit. Track compatible tooling upgrades; do not accept npm's suggested Prisma/ESLint/shadcn major-version downgrades blindly. Use a maintained supported Node runtime for deployment; the current local Node 22.4.1 emits tool-engine warnings.
6. **Production services — release/operations owner.** Rehearse real Stripe test-mode payments/webhooks/refunds, real email verification/reset delivery, private S3/R2 upload/presigned downloads, the authenticated maintenance schedule and alert delivery. Verify HTTPS/cookie Secure flags, migration/release activation, least-privilege credentials, retained-source/artifact backups and restore. Production/cloud ACLs, DNS/TLS, CDN behavior and secret rotation have not been inspected in this local audit.

## Reproduction and verification

- `npm test`: includes `tests/web-security.test.mjs` for origin/media-type/stream limits, callback normalization, HTML email escaping, password length/byte limits, concurrent token consumption, exact webhook signatures and malformed ZIP64 termination.
- `npm run test:security:e2e`: Chrome, OpenSSL (the existing Git installation on Windows), `.env.test.local` and the existing isolated `_test` database are required. The suite creates temporary catalog/account/order data, builds and starts an isolated production app with provider credentials disabled, and uses a local HTTPS proxy with an ephemeral self-signed certificate. It verifies Secure/HttpOnly/SameSite cookies, exercises the attack cases and cleans up the proxy, certificate and fixtures. Certificate trust is bypassed only inside the disposable test browser; real hosted TLS is not verified. Logs are private ignored artifacts under `storage/security/`.
- `npm run test:database`: guarded migration/integration runner for the isolated database only; run sequentially with other heavy checks.
- `npm run lint`, `npm run typecheck`, `npm run build`: repository/source/production checks. Downloaded skill helper scripts under `.agents` are excluded from application lint; source and tests remain included.

The initial browser proof and dependency audit output are retained in ignored `storage/security/` for review. No customer deliverable is replaced. Source lint and the existing test suite are not substitutes for the explicit negative authorization and real-browser checks above.

Development-mode browser attempts exposed repeated streaming/reload timing failures and were not counted as final passes. The isolated production build resolved those harness failures. Its HTTP-only checkout attempt also demonstrated the need for HTTPS to carry production Secure coupon cookies; the final browser suite therefore uses HTTPS rather than weakening cookie security.

Tests used temporary accounts and fixtures, with no live provider calls. The test server, HTTPS proxy and attacker page were stopped and their ephemeral certificates removed. The current implemented application is a candidate for restricted staging verification; public launch remains conditional on the release requirements above and the separate trial/membership roadmap.

Hosting remains in planning, as confirmed by the project owner. The [restricted staging checklist](staging-checklist.md) records the hosted checks without marking them complete or selecting a provider.

After SEC-09 and the compatible dependency updates, the 135-test regression suite, nine production HTTPS/browser scenarios (ten tests with their parent), lint, separate TypeScript check and standard production build were rerun successfully. The seven dedicated quota tests also passed against the isolated database. No hosted service checks were performed.

After SEC-10/11, the 140-test suite, eleven production browser scenarios, lint, separate TypeScript check and standard production build all passed. Browser evidence covers breached-password refusal during registration/change/reset, preservation of reset tokens on refusal, password-change screening outages without session revocation, per-email signup throttling, and denial of draft/image writes to unverified accounts across all eight templates. The first signup-loop test failed because it raced React's form reset; synchronizing each submission with its response and settled button, plus using a fresh proxy-controlled test IP per run, resolved the harness failure. Only the final full pass is counted above. Provider responses remain local fixtures and hosted screening/email availability still needs the staging rehearsal.

After SEC-12, 144 regressions, the isolated MFA database suite, twelve production browser scenarios, lint, type checking and the standard production build passed. Earlier MFA browser attempts stopped at an ambiguous login selector and an assertion that assumed a signed-out session was an object rather than `null`; neither is counted as a full pass. A full system drive was worked around with workspace-local temporary/cache paths, without deleting system files. An initial database connection/build attempt failed; guarded database tests and a read-only catalog connection then succeeded, and the standard build passed on retry. The [MFA guide](admin-mfa.md) records activation, rollback and remaining operational requirements.

The subsequent cache/retention follow-up passed two focused command-wrapper tests, the isolated retention-report integration test and lint. The wrapper keeps tool cache/temp paths in the workspace, handles Windows environment-variable aliases, propagates failures and removes only its own per-run temp directory. No dependencies were installed and no application UI/build changes were made for this follow-up. The live application report ran inside a read-only transaction and returned `SCHEMA_NOT_READY`; no migration or cleanup was performed. The user selected a 30-day proposal; automatic deletion remains disabled.
